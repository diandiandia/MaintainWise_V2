## 第一部分：项目背景与第一性原理业务目标

### 1.1 业务背景与问题痛点
在制造工厂车间一线，传统设备管理系统普遍脱离现场实际，存在以下核心痛点：
1. **录入繁琐卡阻**：录入一台设备前必须预先配置复杂的组织层级树，测试与现场录入极不顺畅；
2. **打卡流于形式与容易篡改**：巡检打卡上传后允许任何人随意修改，失真失信；
3. **经验无法传承给后来人**：维修完成后仅标记“已修复”，不记录真实根本原因与具体排查步骤。老师傅退休或换班后，**后来人（新员工或夜班接班人员）面对同一故障依旧从零摸索**；
4. **部署环境水土不服**：传统软件强依赖 Docker、Linux 内核或外部重型数据库，难以在车间现有的 Windows Server 离线工控机上稳定运行。

### 1.2 第一性原理核心业务目标
本系统旨在打造一套**以设备为中心、以维修病历为资产、以三角色为权责、以极简单端口为底座**的在线化便利系统，实现：
> **“方便登记检修、敏捷派发工单、真实记录闭环、后来人查看病历快速排故维修、单端口离线稳定自启”**。

## 第二部分：用户角色与权限规范 (CR-USR)

### CR-USR-001：三角色严格划分
* **需求描述**：系统必须严格且仅设立三类角色：**系统管理员 (ADMIN)**、**主管工程师 (ENGINEER)**、**维保技术员 (TECHNICIAN)**，杜绝过度复杂的权限树。
* **业务权责**：
  - ADMIN：系统全局参数、全员账号生命周期与密码管理；
  - ENGINEER：设备资产管理、维护计划下发、工单调度、维护单修正、知识库管理、结案验收；
  - TECHNICIAN：现场打卡（上传即锁定）、运行工时抄表、突发故障快速报修、排故病历查阅。
* **验收判据**：系统所有用户必须归属且仅归属于上述三角色之一，界面功能与 API 接口严格按角色隔离。

### CR-USR-002：管理员独占人员账号管理与密码重置
* **需求描述**：员工账号的创建、资料编辑、停用与密码重置，属于系统管理员专属权限。工程师与技术员严禁跨账号修改他人信息。
* **验收判据**：非管理员角色请求人员管理接口返回 HTTP 403；管理员可一键为任何遗忘密码的员工重置新密码。

### CR-USR-003：主管工程师业务中枢管控权
* **需求描述**：工程师负责工厂设备档案的录入维护、层级调整、维护单下发、工单指派改派、完工验收以及排故经验萃取。
* **验收判据**：工程师具备设备台账增删改、层级重命名、工单调度与关闭的完全控制权。

### CR-USR-004：维保技术员现场执行权
* **需求描述**：技术员作为一线现场人员，负责设备日常巡检打卡填报、表盘运行工时抄表、30秒突发故障填报，并被赋能查阅历史维修病历与排故知识库。
* **验收判据**：技术员登录后直达现场工作台，具备打卡、抄表、报修与查阅权限，无权删除设备或修改他人派单。

### CR-USR-005：车间单班次长效登录会话
* **需求描述**：车间作业单班次一般为 8 小时。系统 JWT 令牌有效期必须支持 **8 小时（480分钟）**免密操作，避免工人戴手套作业时频繁重新登录中断业务。
* **验收判据**：登录成功后 8 小时内发起任何正常操作均不应提示会话超时，8 小时后安全登出。

### CR-USR-006：180天密码强制轮换与超期自动冻结保护机制
* **需求描述**：为满足工业系统与等保合规要求，全员登录密码生命周期严格限定为 **180 天**。
  1. 系统记录每个账户的 `password_updated_at`；
  2. 距离 180 天到期日前 3 天起，用户登录成功后界面顶栏浮现醒目黄色预警条，提醒尽快主动修改密码；
  3. 若密码超期超过 180 天仍未修改，系统在下一次登录时**自动将账户冻结 (`is_frozen = true`)** 并拒绝登录（提示“密码已超过180天有效期限，账户已被系统自动锁定，请联系管理员重置”）；
  4. **首次登录独立全屏安全隔离页面**：新创建的用户或重置密码的用户首次登录系统时，实施路由级物理隔离，直接跳转至独立的专属强制改密页面（`/force-change-password`），无任何主导航侧边栏与数据工作台 DOM，彻底阻断敏感车间数据窥探；
  5. **安全改密后强制退出与重新登录认证**：新密码设定成功后，系统必须立即安全销毁当前旧会话凭据（Token），强制登出并重定向至登录页，用户必须使用刚设定的新密码重新登录方可进入系统，达成零信任安全闭环；
  6. 只有管理员有权解冻账户或一键重置密码。
* **验收判据**：
  - 账户改密或创建满 180 天后，登录接口返回 HTTP 403 明确告知密码过期并自动冻结；
  - 剩余 3 天内登录，顶部展示提醒 Banner；
  - 首次登录强制改密以独立全屏隔离页面呈现；提交新密码后系统强制登出，浏览器跳转至 `/login` 且需使用新密码才能成功登录。

## 第三部分：设备信息与资产层级管理规范 (CR-DEV)

### CR-DEV-001：“工厂 - 部门 - 系统”三级架构划分
* **需求描述**：全厂设备必须按照【工厂 - 部门 - 系统】三级标准架构进行逻辑归属划分。
* **验收判据**：每台设备均明确关联其所属的工厂、部门（车间/工段）、系统（产线/系统模块）。

### CR-DEV-002：设备信息字段规范（刚柔兼顾）
* **需求描述**：设备信息字段包含：设备名称、规格型号、数量、设备参数。其中：
  - **【设备名称 (`equipment_name`)】**：**强制必填项**；
  - **【规格型号 (`model_spec`)】**：**强制必填项**；
  - **【数量 (`quantity`)】**：**可选项**（未填写时系统缺省默认为 1）；
  - **【设备参数 (`parameters`)】**：**可选项**（长文本，支持记录功率、电压、转速、介质等工况参数，可留空）。
* **验收判据**：录入时仅输入名称和规格型号即可成功保存；未填数量自动落库为 1；参数为空不报错。

### CR-DEV-003：设备编码非强制项与自动生成
* **需求描述**：设备编码 (`equipment_code`) **不得设为强制项**。若现场暂时没有编码，用户可直接留空，系统后台自动根据时间规则生成唯一的系统内部标识码（如 `DEV-YYYYMMDDHHMMSS`），绝不允许因无编码而阻塞录入。
* **验收判据**：编码留空提交时，系统成功保存并自动分配唯一内部编码，不产生主键或唯一冲突。

### CR-DEV-004：现场维护以设备名称为主进行检索
* **需求描述**：现场工人不习惯也不记得繁杂的编码，日常均以设备名称称呼设备。系统在全局搜索、下拉选择、移动端扫码匹配时，必须**以设备名称为主**进行全文本、前缀与拼音模糊穿透检索。
* **验收判据**：在搜索框输入设备名称关键字，能秒级匹配出结果，且设备名称在界面列表中加粗突出展示。

### CR-DEV-005：设备信息由工程师录入与维护
* **需求描述**：设备台账的建立、资料变更、软删除均由主管工程师（或管理员）负责录入，技术员无权随意新增或删除设备，保证台账权威性。
* **验收判据**：技术员界面无“新增设备”、“编辑设备”、“删除设备”按钮；直接请求接口返回 HTTP 403。

### CR-DEV-006：设备运行时间（工时）由技术员现场抄表录入
* **需求描述**：设备累计运行工时是设备保养周期计算的核心输入。技术员在巡检现场查看表盘累计小时数并录入系统。系统自动读取上一次抄表读数，自动计算本次增量运转时间（`delta_hours = 本次读数 - 上次读数`），记录独立流水并更新设备总运行时间。
* **验收判据**：技术员点击设备【抄表】，输入当前表盘值（如 1250），系统自动计算增量（如 +50 小时）并写入流水表，设备总工时同步递增。

### CR-DEV-007：设备录入极致顺畅（无前置卡阻）
* **需求描述**：彻底消除传统系统“必须先层层配置工厂、车间、产线组织树才能录入设备”的严重卡阻。用户在录入设备时，工厂、部门、系统支持下拉选择已有项，也支持**键盘直接敲入新名称**，保存设备的同时系统自动建立三级归属。表单提供【保存并继续录入下一台】快捷操作，实现 10 秒录入一台。
* **验收判据**：无需进入任何后台组织机构页面，直接打开设备录入弹窗输入新厂部名称和设备名，10秒内完成保存并即时建树。

### CR-DEV-008：工厂/部门/系统层级多次任意重命名（分配给管理员与工程师）
* **需求描述**：工厂名称、部门名称、系统名称在后续实际经营中支持多次任意修改。修改权限分配给**系统管理员**与**主管工程师**。更名时，系统必须在单事务中批量同步更新从属该层级的所有设备，且不得破坏设备原有的历史维修病历与工时流水。
* **验收判据**：工程师在层级树节点点击【重命名】，输入新名称后，该层级下 100 台设备的对应字段一次性批量更新；从属设备的历史病历与工单数据完全保留、关联完好。

### CR-DEV-009：工厂-部门-系统-设备双模展示与穿透钻取
* **需求描述**：优化展示方式，采用“左侧层级导航树 + 右侧数据列表/卡片双模”联动设计。左树展示工厂、部门、系统三级，并标注设备数量徽标；右侧支持表格明细视图与工控大卡片视图一键切换；点击左侧任意节点，右侧瞬间过滤显示。
* **验收判据**：点击左树节点，右侧毫秒级联动刷新；列表模式与卡片模式可无缝切换。

### CR-DEV-010：一机一码自动生成与二维码导出
* **需求描述**：每台设备新增成功瞬间，后台自动调用生成专属高清二维码图片，扫码内容为指向该设备移动端档案的直达地址。支持在界面预览和批量导出打印。
* **验收判据**：新增设备后 `qr_code_url` 字段自动生成并可访问；手机扫码直接打开该设备档案与病历。

### CR-DEV-011：间歇运行与持续运行双模维护预测机制
* **需求描述**：车间设备工况存在两类典型场景，系统必须提供双运行模式 (`running_mode`) 支持：
  1. **持续常开型 (`CONTINUOUS`)**：设备 7x24 小时不间断运行，倒计时按自然日历钟点连续折算；
  2. **间歇开启型 (`INTERMITTENT`)**：工程师每天开机 2~8 小时不等，设定固定工时周期（如每运行 100 小时需要保养一次）。
  - **自适应提前预警 (`advance_warning_hours`)**：支持为每台设备设定提前预警小时数（缺省默认为 20 小时）。当剩余运行时长 $\le$ 预警小时数时，系统自动亮起黄色【即将到期】徽标并触发预警；若剩余时长 $\le 0$，系统亮起红色【已逾期】并触发联锁报警。
  - **14天滑动加权日均运行工时智能预测**：针对间歇设备开机时间不固定痛点，系统基于该设备过去 14 天的实际抄表历史，自动计算滑动加权日均运行时间 $T_{\text{avg}}$，并自动折算出该设备预计还剩多少自然日到达保养阈值，在列表与看板上以“剩余 XX 小时（预计约 Y 天）”直观呈现。
  - **双模工时录入**：支持技术员现场填报“今日增量运转小时 (`delta_hours`)”或直接填报“当前表盘累计读数 (`reading_hours`)”，系统自动计算并累加。
  - **保养完成自动重置**：当设备完成日常维护打卡后，系统自动将 `last_maintenance_hours` 重置为当前 `total_running_hours`，开启新一轮周期倒计时。
* **验收判据**：
  - 设备录入与编辑支持选择运行模式与提前预警小时；
  - 列表与看板精确显示维护进度条、剩余小时数及预计剩余天数；
  - 达到预警阈值时自动标记并支持触发邮件通知；打卡完成维护后自动重置保养基线工时。

### CR-DEV-012：层级级联软删除与资产防护机制
* **需求描述**：在进行“工厂-部门-系统”组织架构清理或关停时，支持主管工程师/管理员在层级树节点上选择级联软删除操作。系统自动级联将该层级下属的所有设备、从属维护单与工单进行安全软删除 (`is_active = false`)，彻底杜绝孤儿数据。
* **验收判据**：
  - 删除带子节点的层级时弹出高危二次确认窗口；
  - 确认后该层级及下属设备全部软删除，历史病历数据永久留存，可由管理员审计恢复。

### CR-DEV-013：组织架构前置规划与用户主动创建层级规范
* **需求描述**：系统必须支持主管工程师与管理员在尚未录入具体设备前，预先规划或独立新建工厂、部门、系统层级架构：
  1. **层级树顶部显式创建入口**：在架构树卡片顶部常驻【+ 创建层级】按钮，支持直接输入全新名称创建整套架构，或选择已有工厂/部门并扩展子级；
  2. **树节点级联快捷建树**：架构树节点悬停提供快捷动作按钮（工厂节点点击 ➕ 新增部门，部门节点点击 ➕ 新增系统，系统节点点击 ➕ 直接为该系统录入设备并自动预填三级归属）；
  3. **零设备空层级展现与穿透引导**：新建好的层级即使设备数为 0，也能在架构树中完整呈现与导航钻取，并在数据列表区展示友好空状态提示（提供【+ 立即录入设备】一键直达引导）；
  4. **双向互通与全量智能补全**：所有自主创建的工厂、部门、系统自动沉淀至底层架构库，录入新设备时的所属工厂、部门、系统下拉列表自动加载所有已建节点，实现架构与资产的双向闭环。
* **验收判据**：
  - 工程师点击【+ 创建层级】可成功保存新工厂/部门/系统；
  - 架构树即时刷新并展示空层级节点（设备计数显示 0）；
  - 点击工厂/部门节点的 ➕ 可自动继承上级名称调出创建窗口；
  - 录入新设备时下拉框可选择刚创建的新层级。

## 第四部分：设备维护单与日常保养规范 (CR-MNT)

### CR-MNT-001：工程师编制与下发周期保养计划
* **需求描述**：主管工程师根据设备技术规格编制保养标准，设定保养周期天数（如 30 天）与标准化检查项（SOP 清单），系统自动推算下次应保养日期。
* **验收判据**：工程师创建计划后，系统自动在工作台生成到期保养倒计时提醒。

### CR-MNT-002：技术员现场巡检打卡
* **需求描述**：技术员按保养计划或现场巡检，逐项检查确认（正常/异常），若存在异常则填写异常说明，并支持拍摄上传现场隐患照片。
* **验收判据**：技术员可在手机或电脑端勾选检查清单并保存。

### CR-MNT-003：维护单上传即锁定只读防篡改机制（核心业务铁律）
* **需求描述**：技术员在现场打卡确认完毕点击【上传提交】后，系统立即将单据状态置为已提交，并将锁定标志位置为已锁定（`is_locked_for_tech = true`）。**技术员端立即移除编辑入口，变为完全只读；技术员严禁且无法再次修改已上传的维护单**。
* **验收判据**：
  1. 前端：技术员登录界面无“编辑”、“修改”、“撤回”按钮，仅显示“查看”并带有金色锁形徽标；
  2. 后端：技术员直接向维护单修改接口发送 PUT 请求时，系统直接拦截并返回 **HTTP 403 Forbidden**，严格防止现场数据伪造与被动作弊。

### CR-MNT-004：工程师独占维护单修改权与强制留痕批注
* **需求描述**：维护单上传锁定后，若确实存在误录或工程师复核发现数据不实，**唯一拥有修改权限的角色为主管工程师**。工程师在修改维护单时，**系统强制要求填报“修改原因与复核批注 (`revision_reason`)”**，不填禁止保存。
* **验收判据**：工程师点击修正维护单，修改原因输入框为强制必填项；修改后单据记录修改工程师、修改时间与修改原因，完整展示在病历中备查。

### CR-MNT-005：巡检异常联锁自动派发维修工单
* **需求描述**：技术员在巡检打卡时，若勾选了异常项并确认提交，系统在**同一底层事务中自动派生创建一张突发维修工单**，将设备状态自动置为 `REPAIRING`（维修中），实现隐患发现与抢修调度的无缝闭环。
* **验收判据**：提交异常维护单后，系统自动新增一条来源为 `INSPECTION` 的工单，设备主表状态自动变为维修中，设备看板同步告警。

### CR-MNT-006：动态自定义检查项目标准 (SOP 动态定制与判定)
* **需求描述**：不同设备具有迥异的物理结构与工况要求，巡检检查项目标准绝不能是写死的静态内容。
  1. 系统必须支持用户在打卡或编制规范时，**动态增减检查项目**（如“检查电机表面温度是否 < 65℃”、“检查气缸润滑油位是否正常”等）；
  2. 每一检查项均由用户动态命名，并支持单选标记【合格】或【异常】；
  3. 若判定为【异常】，支持直接填写异常现象说明与拍照；
  4. 支持按照【工厂-部门-系统-设备】层级级联检索精准定位设备，解决车间设备重名或归属混淆问题。
* **验收判据**：
  - 维护打卡支持动态添加、删除自定义检查项；
  - 级联筛选器支持按厂部系统精确定位设备；
  - 检查结果合格/异常判定联动异常单派发。

## 第五部分：突发故障报修与维修工单规范 (CR-WO)

### CR-WO-001：全员 30 秒极速突发故障报修
* **需求描述**：车间任何人（技术员、工程师、管理员）发现设备故障停机，仅需 3 步完成报修：
  1. 选择或扫码定位设备；
  2. 录入一句话故障现象（如“主轴承发烫震动超标”）；
  3. 选择紧急程度（普通、严重、紧急）并提交；
  提交后系统立即将设备状态自动置为 `REPAIRING`。
* **验收判据**：报修表单无多余字段，30秒内即可提交完毕；提交后全厂看板即时出现新工单，设备态变红。

### CR-WO-002：极简四态工单看板流转
* **需求描述**：工单状态彻底摒弃复杂冗长审批，采用工业敏捷四态：
  1. `PENDING` (待派单)：新报修待指派；
  2. `IN_PROGRESS` (排故维修中)：已接单正在抢修；
  3. `PENDING_CONFIRM` (完工待验收)：现场已修好，待工程师试车复核；
  4. `CLOSED` (已闭环归档)：工程师验收合格结案。
* **验收判据**：系统提供四列可视化看板，工单卡片随状态流转清晰移动。

### CR-WO-003：双轨调度机制（工程师指派 + 技术员主动抢单）
* **需求描述**：对于待派单工单，支持主管工程师一键指定承修人；同时也支持当班技术员在看板上点击【自主接单】进行抢单。
* **验收判据**：工程师可指派任何有效技术员；技术员可一键接单并将工单推进至 `IN_PROGRESS`。

### CR-WO-004：维修复盘根本原因与排除步骤强制闭环（后来人核心经验资产）
* **需求描述**：承修人现场排故完成后提交完工报告，**严禁仅填“已修好”形式主义结案**。系统强制承修人填报：
  - **【故障根本原因 (`root_cause`)】**：**强制必填**（如“冷却水道水垢堵塞导致轴承干热抱死”）；
  - **【详细排除步骤 (`solution_steps`)】**：**强制必填**（详细记录排查过程、拆卸顺序、处理动作与调试参数）；
  - 【更换备件 (`spare_parts`)】：选填规格与数量；
  - 【维修耗时 (`repair_duration_minutes`)】：选填分钟数。
* **验收判据**：根因与排除步骤未填报时，提交完工按钮置灰或报错；填报后工单流转至 `PENDING_CONFIRM`。

### CR-WO-005：主管工程师现场试车验收结案与设备状态恢复
* **需求描述**：设备修好后，必须由主管工程师到现场确认设备试车平稳无异响发热，点击【复核结案】。结案后工单标记为 `CLOSED`，**设备主表状态自动恢复为 `RUNNING` 正常运行**。
* **验收判据**：仅工程师有权执行结案确认；确认后关联设备状态自动变绿恢复正常。

### CR-WO-006：现场维护单编辑纠错与典型案例知识标定机制
* **需求描述**：
  1. **已编辑工单支持纠错修改**：在工单流转过程中（如待派单或维修中），若录入人员发现填写的故障现象、紧急程度有误，创建人或工程师有权点击【编辑】重新修改保存，避免错单将错就错；
  2. **完工待验收态穿透查看详情**：工单流转至“完工待验收”状态时，卡片必须支持点击弹出完整详情抽屉/对话框，供主管工程师试车前复核承修人填写的根本原因、排除步骤与备件消耗明细；
  3. **已闭环归档案例标定**：当工单完成试车验收进入“已闭环归档”后，工程师进行复盘，若认为该工单具有极高的代表性与排故参考价值，可点击【标定典型案例】（`is_typical_case = true`）。标定后系统自动将其推荐进入“后来人知识库”，让新人能够随时检索汲取。
* **验收判据**：
  - 待处理工单支持编辑更新接口；
  - 完工待验收工单支持弹窗查看全部复盘字段；
  - 已归档工单支持标定为典型案例并自动同步至后来人知识库。

## 第六部分：后来人终身维修病历与知识库规范 (CR-KB)

### CR-KB-001：后来人第一性原理——终身电子维修病历时间轴
* **需求描述**：系统必须以设备为主线，将该设备终身经历的：
  1. 历次突发维修记录（包含故障现象、根本原因、排除步骤、更换备件）；
  2. 历次维护打卡记录（包含检查项明细、异常说明、工程师修改批注）；
  3. 历次运行工时抄表流水（包含表盘读数、增量运行时间）；
  自动按时间倒序汇聚成一条**连续动态的电子维修病历时间轴**。新员工或夜班接班人员扫码即可查看前人所有修复历史，5分钟内锁定排查思路。
* **验收判据**：设备详情页点击【终身病历档案】，按秒级倒序展示所有维修、维保、工时事件卡片，根因与排查步骤重点高亮排版。

### CR-KB-002：结案工单一键萃取至排故知识库
* **需求描述**：对于具有典型代表性的排故案例，主管工程师在工单结案后可点击【⭐ 萃取至知识库】，系统自动将故障现象、根本原因、排除步骤抽取生成通用知识库条目，并支持标记“置顶金标”。
* **验收判据**：工程师一键提炼知识库成功，知识库列表新增条目，全厂工人均可检索抄作业。

### CR-KB-003：报修输入实时智能排故方案推荐
* **需求描述**：工人在报修输入故障描述时（如输入“变频器过流报警”），系统后台即时检索知识库与过往高分病历，在界面右侧实时浮现“后来人排故参考”推荐卡片，提示可能原因与排除方法，实现“尚未发单，排查方案已至”。
* **验收判据**：报修输入文字触发防抖查询，300毫秒内返回匹配案例并在界面友好展示。

## 第八部分：跨平台部署与环境工程约束 (CR-CON)

### CR-CON-001：开发在 Linux，最终部署在 Windows Server 离线环境
* **需求描述**：开发测试环境基于 Linux，而目标交付运行环境为 Windows Server 2016/2019/2022/2025 离线纯局域网工控机。所有技术选型与实现必须将此作为**刚性工程约束**。
* **验收判据**：代码中不得使用任何 Linux 专有系统调用或强依赖，路径必须兼容，无外网依赖。

### CR-CON-002：双轨同构一键部署工具集（Linux + Windows）
* **需求描述**：系统根目录与部署目录下必须同时提供完备的 Linux Shell 部署脚本与 Windows 批处理部署工具箱。包含全自动安装向导、环境初始化、前台测试、后台服务安装、启动、停止、卸载与热备份脚本。
* **验收判据**：
  - Linux 环境执行 `一键部署_Linux.sh` 顺利安装并运行；
  - Windows 环境双击 `一键部署_Windows.bat` 顺利完成环境初始化并在 8000 端口启动。

### CR-CON-003：Windows 生产端零 Node.js / 零外部编译依赖
* **需求描述**：前端所有 Vue 3 / TypeScript 代码必须在 Linux 端预先构建打包为静态资源（`frontend/dist`），由 FastAPI 单端口统一宿主托管；Windows 生产端仅需标准 Python 运行时，无需安装 Node.js、npm、Webpack 或 Visual C++ 编译器。
* **验收判据**：纯净 Windows Server 仅安装 Python 3.10+，即可直接通过批处理运行系统，无需额外安装 Node.js 或构建工具。

### CR-CON-004：单端口全栈交付 (:8000)
* **需求描述**：系统对外仅暴露单个 TCP 端口（默认 8000），同时承载前端单页面应用 (SPA)、RESTful API 接口以及 `/uploads` 附件访问，彻底避免多端口反向代理和车间防火墙配置困难。
* **验收判据**：局域网客户端仅访问 `http://<IP>:8000` 即可使用全部功能，无跨域问题。

### CR-CON-005：Windows 批处理编码与换行规范
* **需求描述**：所有供 Windows 执行的 `.bat` 批处理脚本必须采用 **CRLF (Windows 标准换行)**，且文件第一行必须声明 **`chcp 65001 >nul`**，确保在中文版 Windows CMD 中输出汉字绝不乱码。
* **验收判据**：批处理在 Windows 命令提示符运行中文无乱码，无行尾解析错误。

### CR-CON-006：Linux 后台守护持久化与无交互进程生命周期管理
* **需求描述**：针对轻量容器、开发机或未配置 systemd 的 Linux 生产环境，系统启动必须支持基于 `setsid` 与标准输入脱离的独立会话后台持久运行机制。用户退出 Shell 终端或断开 SSH 连接后，服务绝不中断。同时系统根目录常驻四个快捷运维脚本（`./start.sh`、`./stop.sh`、`./status.sh`、`./restart.sh`），提供精准的进程 PID 追踪、端口释放与日志诊断支持。
* **验收判据**：
  - 执行 `./start.sh` 后，服务在后台稳定监听 8000 端口，并生成 `maintainwise.pid`；
  - 退出 SSH 或关闭终端，后台服务 100% 持续稳定运行；
  - 执行 `./status.sh` 实时报告运行状态，`./stop.sh` 彻底释放端口。
